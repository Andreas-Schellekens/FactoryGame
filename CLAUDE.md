# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — start the Vite dev server with hot reload
- `npm run build` — production build to `dist/`
- `npm run preview` — serve the production build locally
- `npm run voice` — record DELTA's voice lines with ElevenLabs (`scripts/voice.mjs`; `-- --dry` lists what it would do; needs a `.env`, see `.env.example`)

There is no test runner, linter, or formatter configured.

## Overview

**Protocol: Selene** — a Factorio-style factory game with a story campaign (vanilla JS + Vite), rendered in 2.5D with [Three.js](https://threejs.org): real 3D models under a fixed-angle isometric orthographic camera. Models are CC0 packs by Kenney (see `CREDITS.md`). The player builds a production chain on a grid: **ore node → extractor → smelter → press / foundry → assembler → Dispatch Pad** (the `sink` machine type), joined by belts. The pad pays credits for sellable goods; credits fund more machines and tier upgrades. Deliveries also advance the **campaign**: five Protocol: Selene phases (build a cannon to "save Earth from the falling Moon"), each requiring item deliveries and unlocking buildings. An AI guide, **DELTA**, narrates, teaches and drives the satirical plot (*NILE*, the Network for Infrastructure, Logistics & Engineering, is slowly revealed to be *NIHIL*, the Network for Infrastructure, Heavy Industry & Logistics). Story bible and iteration roadmap: `docs/DESIGN.md`. All in-game text is English.

The production chain (all defined in `grid.js`):
- Ore deposits sit on the map as terrain (`cell.resource`): `ironOre`, `copperOre`, `coalOre`, and `sulfurOre`, which only appears at the reveal (where NIHIL drained the pond).
- **Extractor** (must be placed on an ore node) mines that ore.
- Every processor runs **one recipe chosen in its panel** (`machine.recipe`, from the per-type `RECIPES` table) and only accepts that recipe's inputs:
  - **Smelter**: `ironOre→ironIngot` or `copperOre→copperIngot`.
  - **Press**: `ironIngot→ironPlate` or `copperIngot→copperWire`.
  - **Foundry**: `ironIngot + coalOre → steel`.
  - **Assembler**: `ironPlate + copperWire → circuit`; `steel + 2 copperWire → capacitor` (1.5× slower); `steel + ironPlate + copperWire → motor` (three inputs, 2×); `2 circuit + steel → advancedCircuit` (research-gated, 1.5×); `steel + explosive + advancedCircuit → seleneShell` (4×).
  - **Fabricator**: `circuit + copperWire → dataCartridge`. **Lab** reads `dataCartridge`s into `RESEARCH_PER_ITEM` research points (no item output).
  - **Mixer**: `sulfurOre + coalOre → explosive`.
- **Generator** burns `coalOre` from its buffer to feed the global power network (see below).
- **Sink / Dispatch Pad** accepts anything in `SINK_VALUE` plus whatever the active campaign phase requires, pays the **market price** (each sale pushes that item's price down, prices recover over time, see `MARKET_*` in `config.js`), and credits the phase. Priority Request bonuses are paid in full.

Two routing machines move items without transforming them: a **splitter** (1 input on the back → 3 outputs: straight ahead + both perpendiculars, round-robin) and a **merger** (3 inputs: back + both perpendiculars → 1 output straight ahead). `dir` is the primary flow axis for both.

**Power** is a global network, not an item: each tick supply (`BASE_POWER_SUPPLY` "starter grid" + `POWER_PER_GENERATOR` per fueled generator) is compared to the demand of powered machines (`POWER_DRAW`: smelter, press, foundry, assembler, fabricator, mixer, lab) that currently want to work and are switched on; the ratio is clamped to a `throttle ∈ [0,1]` that scales their progress, so a small shortfall only slows the factory. Demand above `OVERLOAD_RATIO` × supply for `OVERLOAD_TICKS` in a row **trips the breaker**: every powered machine stops until the player lowers the load (switch machines off in their panels, or add generators) and presses Reset on the power gauge (`resetBreaker()`; a reset while still overloaded trips again within a second). Extractors are deliberately unpowered so the bootstrap chain can't brown itself out.

The **campaign** (`campaign.js`) is the main progression layer: you start with belt/extractor/smelter (`STARTING_BUILDINGS`); each completed phase in `PHASES` unlocks more (press/assembler/splitter/merger → foundry/generator → fabricator/lab → mixer), and every phase asks for the products of the chain the previous one unlocked (ingots → plates and circuits → steel and capacitors → motors and advanced circuits → Selene Shells and capacitors), so the whole factory has to be built. The table is in `docs/DESIGN.md`. Completing the last phase ends the game (the ending cinematic and mission report, then sandbox).

**Research** is the secondary layer: Fabricator-made Data Cartridges go into a lab, points buy permanent unlocks via `unlockTech(id)` — `fastBelts` (movers phase runs twice per tick), `advancedProduct` (enables the advancedCircuit recipe), `tier4` (raises the upgrade cap from `MAX_TIER - 1` to `MAX_TIER`). Costs live in `config.js` `TECH_COST`. (Buildings are never research-gated.)

An **order** system ("Priority Requests", from phase 2 on) layers a timed bonus on top: a demand for N of a product the current phase can make (`ORDER_POOL`) within M ticks pays a one-off reward on completion (see `grid.js` order state and `config.js` `ORDER_*`).

Some older comments may be in Dutch.

## Architecture

The simulation (`grid.js`) is the source of truth and has **no knowledge of Three.js or the DOM**. Everything else reacts to it. Each `src/` file has one job:

### `src/grid.js` — simulation core
- Owns the `grid` (2D array of `{ machine, item, resource }` cells) and the exported `score` (money). `score` is a live ES-module binding — other modules `import { score }` and read the current value directly. Same pattern for `tickCount` (the monotonic sim clock, advanced once per tick), the `order` object, the `power` network state (`{ supply, demand, throttle }`, recomputed every tick, never saved), the `research` state (`{ points, unlocked: { fastBelts, advancedProduct, tier4 } }`, saved), the campaign `project` state (`{ phase, delivered, complete }`, saved — `phase` indexes `PHASES`, `delivered` counts the active phase's required items) and lifetime `stats` (`{ produced, delivered, researchEarned }`, saved; read by the story director) — all mutated in place.
- A **machine is an object**: `{ type, dir, tier, buffer, pendingOutput, progress, produces?, toggle?, fuelTicks?, recipe?, off? }`. `type` ∈ `belt | splitter | merger | extractor | smelter | assembler | fabricator | generator | lab | sink`. `recipe` is the chosen `RECIPES` id (machines that have recipes); `off` marks a machine the player switched off (no work, no power draw; it still takes deliveries until its buffer is full). `dir` ∈ `right | down | left | up` (output / primary-flow direction). `buffer` holds input-item counts (capped at `BUFFER_CAP`); items inside a buffer have **no sprite** (they were `consume`d on entry). `toggle` is the round-robin cursor for splitters/mergers; `fuelTicks` is the generator's remaining burn. Tier (1–`MAX_TIER`) scales processing speed via `PROCESS_TICKS`; `progress` may be **fractional** on powered machines (it advances by `power.throttle`).
- `updateFactoryLogic()` advances one tick and **returns `FactoryEvent`s** (`spawn` / `move` / `consume`). It first does `tickCount++`. Phases run in a fixed order: (1) sinks consume their item, pay `SINK_VALUE`, credit the active order, `project.delivered` and `stats.delivered`, then `checkPhaseComplete()` advances `project.phase` once every requirement is met (the `phase` bump is the only completion signal) — then the order resolves (complete pays `order.reward`, or fail past the deadline) → (2) processors (incl. generator and lab) absorb their input-slot item into their buffer → (3) **movers** (belts, splitters, mergers) relocate items, reverse scan — the whole phase runs **twice** when `fastBelts` is unlocked → (3.5) **power**: generators burn coal (one `coalOre` lasts `GENERATOR_FUEL_TICKS`) into `power.supply`, powered machines with a runnable recipe add their `POWER_DRAW` to `power.demand`, and `power.throttle = clamp(supply/demand, 0, 1)` → (4) processors advance `progress` by `throttle` (unpowered: by 1) and eject the result (counted in `stats.produced` when crafted, even if the output is blocked); a completed **lab** recipe adds `RESEARCH_PER_ITEM` to `research.points` instead of ejecting → (5) extractors mine. Ejection/mining happen *after* movers so a newly produced item waits a tick before moving (no same-tick double-hop). The event list is the simulation's only output channel; the renderer reacts to it rather than diffing the grid.
- Splitters push their item to one of `splitterOutputs(dir)` (`[dir, ...PERP[dir]]`) round-robin; mergers push their held item forward then pull from one of `mergerInputs(dir)` (`[OPPOSITE[dir], ...PERP[dir]]`) — pull-only (`cellAccepts` is false for a merger), gated by `outputsToward()` so they only take from neighbours aimed at them. `toggle` advances past the side actually used so a blocked side can't skew the balance.
- `cellAccepts(cell, itemType)` is the single gate for all item transfer (belts, splitters, machine inputs, sink): it enforces empty slot, the machine's chosen recipe (only its inputs, and only once its `tech` gate is researched), buffer cap, coal-only generator, and the sink's `sinkAccepts` (`SINK_VALUE` ∪ active phase requirements). Recipes live in the exported `RECIPES` table (`{ [machineType]: [{ id, inputs, output, time?, tech? }] }`; output `null` = research points); `machineRecipe(m)` gives a machine's recipe, `recipeFor(m)` it only when the buffer holds a full operation's inputs, and `processInterval(m)` multiplies `PROCESS_TICKS` by the recipe's `time`.
- Build/economy API: `canBuildMachine` / `buildMachine(x, y, type, dir, recipe?)` (extractor requires `cell.resource`; every type must pass `isBuildingUnlocked(type)`, derived from `project.phase`; the recipe falls back to the first unlocked one), `setRecipe(x, y, id)` (scraps buffered inputs the new recipe doesn't use), `setMachineOn(x, y, on)`, `placeBelt` (drag-laying), `removeMachine` (refunds the base `MACHINE_COST` so the economy can't soft-lock; returns `consume` events for any destroyed in-transit item; the sink is protected), `canUpgrade` / `upgradeMachine` / `upgradeCost` (caps at `MAX_TIER - 1` until the `tier4` unlock), and `machineProgressFraction` (for the renderer's progress bars).
- Research API: `research` (live state) and `unlockTech(id)` — checks/spends points against `TECH_COST` and flips the permanent `unlocked` flag. The HUD pulls both via `getState()`.
- Power API: `power` (`{ supply, demand, throttle, overload, tripped }`; `overload` 0..1 is the countdown to a trip) and `resetBreaker()`.
- Market API: `market` (`{ pressure: { [item]: recent sales } }`, decays every tick, saved) and `salePrice(type)`; the pad's `consume` events carry `paid` (what that delivery earned, used for the floating credits).
- Panel queries: `machineStatus(x, y)` → `{ code, missing? }` with `code` ∈ `off | tripped | blocked | fuel | input | locked | slow | working | idle` (feeds the panel's status line, the status bubbles in 3D and the production overview's machine counts), `machineRates(x, y)` → per-minute `inPerMin` / `outPerMin` (and `points` for a lab), `kw` (negative = supply) and `next` (the next tier's rates, or null).
- `flow` (`{ made, used, sold }` running totals per item, never saved): extractors and finished recipes add to `made`, consumed recipe inputs and burnt coal to `used`, the pad to `sold`. main.js samples it for the production overview.
- Order API: `order` (state: `active`, `status` ∈ `none | active | completed | failed`, `target`, `reward`, `delivered`, `startTick`, `deadlineTick`) and `startOrder({ target, ticks, reward })` — grid.js counts deliveries and pays the reward; *which* order to issue (difficulty/cadence) is policy chosen in `main.js`. The `status` flip is the only completion/failure signal — the HUD polls it via `getState()`.
- Campaign API: `project` (also `ending`: null | 'moon' | 'hq', the target chosen at the end, and `company`, the player's company name after the 'hq' ending; both saved), `stats`, `isBuildingUnlocked(type)`, `currentPhase()`, `setEnding(kind)`, `setCompany(name)`.
- Ports API (read-only, mirrors the transfer rules; feeds the renderer's port arrows and the inspector): `portsFor(type, dir)` → `{ in: [sides], out: [sides] }` (processors: in = back + sides, out = front; generator/lab/pad: in on all sides, no out; extractor: out only; splitter: in back, out front + sides; merger: in back + sides, out front; belts: none), `machinePorts(x, y, type?, dir?)` → `[{ side, kind: 'in'|'out', connected, blocked }]` for a placed machine or a build preview (`connected`: a neighbour actually takes from / sends into that side; `blocked`: a finished product is stuck in `pendingOutput`), and `machineIO(type)` → `{ takes, makes }` item types.
- Plot and river: you may only build inside `plotRect(phase)` (`config.js` `PLOTS`, one rectangle per phases completed, growing to the whole map) — `inPlot(x, y)`; cells along the `RIVER` polyline are `cell.river`, and `cell.water` (unbuildable) until `RIVER.damPhase` phases are complete (`applyRiver(phase)`, run on completion and load, before `revealOre`). `canBuildMachine` / `placeBelt` refuse water and cells outside the plot.
- Groups (the select tool): `machinesIn(x0, y0, x1, y1)` (all but the pad), `planGroup(cells, anchor, to, rot, mode)` → `{ moves: [{ from, to, type, dir }], bad, cost, ok }` (the cell `anchor` lands on `to`, turned `rot` quarter turns clockwise; a move may overlap its own cells, a copy needs empty cells, unlocked buildings and the credits), `applyGroup(plan, mode)` (move: machines keep their buffer, tier and the item on them, which gets a `move` event; copy: fresh tier-1 machines with the same recipe, direction and on/off, paid for) and `removeGroup(cells)` (refunds).
- Ore fields: `initGrid()` lays every `ORE_FIELDS` entry without `fromPhase`; `revealOre(phase)` lays the ones whose `fromPhase` has come (called on a phase completion and on load) and bumps the exported `oreRevision`, which the renderer watches to add ore views.
- Terrain: `initGrid()` also marks the `CANNON_AREA` cells `blocked` (the reserved Selene construction site): `canBuildMachine`/`placeBelt` refuse them and `loadState` skips saved machines there. `cellHash(x, y)` is the deterministic per-cell random used for map and decor layout.
- Save/load API: `serialize()` returns a plain JSON-able snapshot (version `SAVE_VERSION` = 5, `score`, `tickCount`, `order`, `research`, `project`, `stats`, `market`, and only the non-empty cells — terrain is recreated by `initGrid()`); `loadState(data)` rebuilds the grid (re-`initGrid()` then overlays saved machines onto `makeMachine` defaults), resets `research`/`project`/`stats` to defaults before overlaying the saved values, and **returns `spawn` events for in-transit items only** — buffer contents and `pendingOutput` have no sprite, so they are never spawned. `power` is not saved (recomputed each tick); generator fuel persists via the machine's `fuelTicks`. Returns `null` on missing/version-mismatched data (saves from an older version are not loaded; the title screen only offers a compatible save). The breaker is reset on load.

### `src/renderer.js` — the 3D view (Three.js)
- `await createRenderer(container, { onProgress })` loads the models (`assets.js`), builds the scene (lights, environment, ore nodes) and returns `{ canvas, rig, applyEvents, tweenItems, draw, reset, pickCell, projectCell }`. World mapping: cell `(x, y)` is centred on world `(x + 0.5, 0, y + 0.5)`; grid "down" (+y) is world +z; model forward is +z, so `dir` → yaw via `YAW`.
- **Machine views** are synced from the grid every frame (`syncMachines`): each cell's view is keyed by a signature (`type|dir|beltShape`) plus the machine object's identity, and rebuilt only when that changes. `buildView(m, …)` composes Kenney models per type (belt / corner belt, router cross + arrows for splitter/merger, extractor frame + piston over its ore rock, smelter + chimney + glowing mouth, assembler + cog, lab + dish, generator cooling tower + glow, Dispatch Pad platform + a compact drop-zone marker: a short light cone, a bobbing downward chevron sprite and a pulsing ring) and a status cluster of sprites (progress bar, tier dots, and a **status bubble** from `machineStatus`: grey "…" waiting for an ingredient, orange "!" output blocked, a red bolt when the breaker tripped, amber in a brownout, a power symbol when switched off, a lock when the recipe needs research; nothing while it works). The Fabricator is a machine bed with a procedural yellow robot arm (`robotArm()`) that swings once per operation, and a teal data reader. The **Press** is Factory Kit pistons squashed into a bed with a yellow die (`button-floor-square`), two columns and a crown with a dark cylinder on top, plus a ram on a chrome rod; its frame and ram are baked into one mesh per material, shared by every press (`baked(key, build)`: the pistons are three meshes each). The **Foundry** is a soot-tinted `machine-connection-hole` with molten steel glowing in its roof hole, a glowing mouth like the smelter's, and a tall brick-red `chimney-basic` stack at the back. The **Mixer** (NIHIL's, unlocked after the reveal) is an open gunmetal vat (`space/rocket_fuelA`, alarm-red rim, stretched deeper) full of glowing sickly-green liquid, a bridge with a yellow motor and a stirring paddle, and a feed pipe with a valve wheel; its static procedural parts are merged per material once (`mixerFixed`). Procedural parts share geometry (`partGeo`) and the arm's materials; only glowing surfaces get a material per machine. Corner belts use the native `conveyor-stripe-corner` (connects the −x and +z sides) rotated by `cornerFit()`.
- **Belt motion:** a shared chevron texture on flat ribbons (`ribbon()`: v runs along the centreline, so straight and curved belts scroll at the same density) whose offset advances one cell per tick (two with Express Belts).
- **Items:** `items` (`Map<itemId, { obj, anim }>`) bridges simulation items to meshes from `createItemMesh`. `applyEvents(events, tickMs)` creates/tweens/destroys them — a second `move` in one batch (fastBelts) extends the tween; heights come from the cell's machine (`surfaceY`). `reset()` drops all item meshes (used on load).
- An internal animation clock (`animMs`, scaled by `state.speed`, frozen while paused) drives pistons, cogs, dishes, smelter/foundry glow, generator glow, the mixer's liquid and the pad beacon off `machineProgressFraction` and `power.throttle`. The press ram runs on its own per-view cycle (one stroke per operation, `opMs()` from `PROCESS_TICKS` × the recipe's `time`, scaled by throttle; progress itself only moves per tick): it drops fast onto the die and lifts slowly while `machineStatus` says working, and eases back up otherwise. Chimney smoke per type comes from `SMOKE` (smelter grey puffs, foundry thick dark smoke); fueled generators steam; the foundry's melt flickers and spits a few sparks; the mixer's paddle turns, its liquid pulses, green bubbles well up (`effects.bubble`) and a faint toxic haze rises. Furnace mouths, the foundry's melt, the mixer's vat and generator tops carry additive halo sprites (fake bloom).
- **Ore nodes** are built from the grid's resources and re-synced whenever grid.js's `oreRevision` moves (`syncOre`): a cell that gained a resource gets a view (crystal rock tinted by `ORE_TINT` + a faint stain), one that lost it drops it. A field laid during play (the sulfur under the drained pond, at the reveal) rises cell by cell from its centre outward after ~1.4 s, with dust and yellow sparks (`orePops`, `animateOre`); on load (`quiet`) it is simply there. New ore hides that cell's flowers (`env.markOre`) and re-lays the focus rings. An extractor shrinks the rock under it.
- **Phase mood:** `MOODS` (per phases completed) sets hemisphere/sun/rim light colours, intensities, the sun's direction, exposure and environment intensity — sunny morning → afternoon → golden hour → dusk → red night → blood red. `applyMood()` eases toward it (snaps on load); the pad beacon turns red at phase ≥ 4. `draw()` forwards phase changes to `env.setPhase` / `cannon.setPhase` (a single step forward animates, anything else is instant).
- **Juice:** new machines pop in (`easeOutBack`) with a dust puff and (non-conveyors) a small camera shake, demolished ones shrink and sink with a puff (`dying`), upgrades sparkle and bounce, deliveries float "+N credits" over the pad (batched per 450 ms), and a completed phase shakes and punches the camera. `floatAt(x, y, text, color)` floats text over a cell (main.js: build/upgrade cost, demolish refund). A `quiet` flag (first sync, and after `reset()` on load) builds views without juice. Every built cell except conveyors (belt/splitter/merger — `CONVEYORS`; those only hide the flowers via `env.coverCell`) is paved (`env.paveCell`), smelters, foundries and generators also scorch (`env.scorch`), mixers leave a green-yellow chemical stain (`env.scorch(x, y, 'toxic')`); `saveVisual()`/`loadVisual()` persist the paving. `stats()` returns the last frame's draw calls/triangles.
- **Overlay:** cursor outline, a signal-orange frame around the machine whose panel is open (`state.selected`), the selection (`updateSelection`: the box being dragged, a square frame on every selected machine as one InstancedMesh, and the carried group as ghost models at their landing cells, red where they don't fit), `quietNext()` (the next machine sync is silent), a build ghost (the real model in a green/red ghost material, cached per tool+dir inside a wrapper group that pops in on a tool change, turns from the old direction on R, and wiggles on `nudgeGhost()` when a build is refused), a tinted box for erase/upgrade, and pulsing focus rings around `state.focus` (the active objective's target: an ore type or `'sink'`; only the field nearest the pad is ringed). All hidden while `state.cinematic`.
- **Ports:** small flat arrows at machine edges (instanced, drawn over the world): teal = input, orange = output, bright when `machinePorts` says something is hooked up, dim when not, red and pulsing when the output is blocked. Shown for every machine while a build tool is held, always for the hovered machine and for the build ghost (its would-be connections), and blocked outputs always. An output and the neighbouring input line up into a two-arrow chain across the edge. Refreshed every ~120 ms.
- **Ending API** (driven by the HUD's timeline): `lookAtCannon()` (while the player chooses the target); `frameCannon({ radius, top, target })` — for `target: 'hq'` it cuts to a view from the south-west with the cannon and NIHIL HQ (`env.hqPoint()`) in frame and turns the turret to it (`aimAtWorld`); `fireCannon({ target })` — for 'hq' it launches a glowing shell on an arc (`launchShell`, `HQ_FLIGHT_MS` in config.js) whose impact (`hitHQ`) throws a fireball, a flash light and a shockwave and brings the tower down (`env.ruinHQ()`). With `project.ending === 'hq'` (once the shot has landed) the lighting eases to the `FREED` dawn mood, the pad beacon goes back to NILE blue, and a loaded save shows the ruin (`env.setHQRuined`). The Moon target: `frameCannon({ radius, top })` cuts the camera to the cannon, finds a patch of clear sky in the upper frame by raycasting against the world (the sky only shows beyond the valley's far edge in this view), returns it as the Moon's page point and swivels the turret to aim there; `chargeCannon(level)`, `fireCannon()` (shake + punch), `muzzlePage(along)`, `releaseCinematic()`.
- `pickCell(clientX, clientY)` raycasts onto the ground plane; `projectCell(x, y)` gives a cell centre's page coordinates (used by tests).
- `icons`: build-menu pictures (`{ [machineType]: PNG data URL }`), rendered once at startup by `renderIcons` from the real machine views (game camera angle, output to the lower right; the belt carries ore, the extractor stands on its crystal), plus the edit tools as small 3D props in the same materials (`TOOL_PROPS`: `upgrade` = a machine with two gold chevrons rising out of it, `erase` = a sledgehammer landing on a breaking crate, `rotate` = a belt with a clockwise teal arrow round it; framed by their silhouette rather than their bounding sphere). They are drawn by the main renderer into a corner of its own canvas before the first frame and copied out in the same task: no second WebGL context, and the same tone mapping as the game. main.js passes them to the HUD.

### `src/assets.js` — models + item meshes
- `MANIFEST` maps keys to Kenney GLBs in `public/assets/kenney/` with a `fit` (larger footprint side, in cells), optional `yaw` and `tint` (recolour by material name — Space/Nature kit materials are named `rock`, `crystal`, `stone`, `grass`, `metal…`). `loadAssets()` normalises each model (centred, standing on y = 0, scaled to `fit`, shadows on) and forces non-metal materials to `metalness 0` (glTF defaults to 1, which renders flat-colour models black). `get(key)` returns a clone sharing geometry/materials. `tintTemplate()` recolours named materials (ore nodes use `ORE_TINT`, incl. `sulfurOre`: pale ochre rock, lemon crystals); on Factory/City Kit models, whose single `colormap` material is a texture atlas, a `tint` multiplies it (the foundry's soot, its brick stack). The 4b machines use `pressBlock`/`pressColumn`/`pressDie` (unit-size Factory Kit pistons and a floor plate, scaled per part), `foundry` + `foundryStack`, and `mixerVat`. `createItemMesh(type)` builds the procedural item meshes, one material per part and same-material parts merged (`merge()`): ore chunks (incl. yellow sulfur), ingot bars, two stacked iron plates, a copper-wire coil on a spool, a steel I-beam, circuit boards, a capacitor can with a cyan band, an orange motor with dark caps and a shaft, three strapped red explosive sticks, the Selene shell (brass case, red driving band, gunmetal ogive), data cartridges.

### `src/environment.js` — the valley and its decay
- `buildEnvironment(scene, assets, effects)` → `{ setPhase(p, instant), update(dt), paveCell, scorch(x, y, tone), coverCell, markOre, savePaved, loadPaved }`. A green valley (`docs/DESIGN.md` "Visual arc"): a greyscale ground texture tinted per phase (`LAND`), a faint build grid, a transparent paving canvas over the buildable area (cannon-site gravel, concrete under built cells, scorch marks), merged cliff walls, the Steward's camp (tents, campfire with halo + smoke; goes out at the reveal), a farm (south rim, west of where the river leaves the grid), the river, a forest and NILE's compound on the east rim. Rim scenery keeps clear of the river (`nearRiver`) and grid flora skips river cells. Per phase: trees switch normal → `_fall` → `_dark` and get felled (they tip over, then become stumps) by a per-tree `fellPhase`; phase-gated props (`addProp(key, x, z, min, max)`) fade in/out — flowers vanish, mushrooms appear at dusk, crops die; compound buildings (`BIG_BY_PHASE`) pop in on lattice slots nearest the pad first; floodlights light up from golden hour; shared nature material colours (grass, leaves, dirt) ease toward `LAND`. Small props cast no shadows (`NO_SHADOW`) and static scenery is merged (`mergeStatic`) to keep draw calls down. The sky is CSS behind the canvas.
- **The river** follows `COURSE`: `config.js` `RIVER.path` carried on over the rim at both ends — it wells out of a rock knoll on the west edge (extra `cliff` blocks above ground, a short cascade down its face, a splash) and drops off the south cliff as a waterfall fading into spray. Its shape is cell-exact: `riverCell(x, z)` is the sim's `cell.river` inside the grid and the same distance + `cellHash` jitter rule along the extended course on the rim; `riverMasks()` rasterises those cells over the world rectangle `MASK` and box-blurs them (red = water, corners just rounded; green = bank, blurred wide) into a `DataTexture`. Two ribbons along a Catmull-Rom of the course (attribute `aRiver` = across, `s` = distance downstream, fall depth, soft edge) are cut by that mask in `onBeforeCompile`-patched `MeshStandardMaterial`s (shared uniforms `riverU`): the bed/bank ribbon (`BED_GLSL`: a narrow band of wet earth + faint damp halo, dark mud under the water) and the water (`WATER_GLSL`, the falls and the spring cascade merged into one mesh: `LAND` water colour, lighter shallows, a foam line, per-lane streaks drifting downstream, faster down the falls). Reeds (instanced cones + cattail heads on the shared `grass`/`woodDark` nature materials) stand at the water's edge and lilies float on it.

### `src/effects.js` — particles and glows
- `createEffects(scene)` → `{ puff, sparkle, smoke, bubble, floatText, update(dt, centre, phase, bounds) }`: a pooled sprite particle system (dust, additive sparks, smoke/steam, the mixer's rising bubbles), floating text sprites, butterflies over the meadow (fewer each phase, none from dusk), falling ash (phase ≥ 3) and rising embers (phase ≥ 4) spawned around the camera target. `haloSprite(color, size)` makes an additive glow sprite. ### `src/camera.js` — isometric camera rig
- `createCameraRig(bounds)`: an orthographic camera orbiting a ground target at a fixed 38° elevation. `panPixels` (drag) + `endPan()` (the view glides on after a middle-drag), `panBy` (keys), `zoomBy`, `rotate(steps)` (90° steps), `focusOn`, `resize`, `target` (live look-at point), and `update(dt)` which eases toward the goal each frame. Juice: `shake(amount)` (trauma that decays; offset + a little roll, strength trauma²) and `punch(amount)` (a zoom kick that springs back). Cinematics: `snap({ x, z, zoom, azimuth })` cuts without easing (default view direction), `shiftPixels(dx, dy, h, { snap })` moves the view by a screen delta.

### `src/gameLoop.js` — the loop
- `startGameLoop(renderer, state, onFrame, onEvents)` runs a **fixed-timestep tick on a `requestAnimationFrame` loop**: clamps the frame time to 0–100 ms (the first frame's timestamp can predate the loop's start after a long startup task, and a negative dt would make every eased value explode), accumulates `dt * state.speed` and calls `updateFactoryLogic()` once per `1000 / TICK_RATE` ms (catching up at most 8 ticks per frame, then dropping the backlog), feeding events to `renderer.applyEvents` with a tween length of one tick of wall time, and to `onEvents` (sound). Each frame then runs `onFrame(dt)` (HUD, director, key-panning) and `renderer.draw(state, dt)`.

### Sound (`src/audio.js` + `synth.js`, `music.js`, `sfx.js`, `ambience.js`, `voiceLines.js`)
All sound is **synthesized with the Web Audio API** (no sample files), so music, effects and ambience share one sound world and follow the arc. None of it knows the simulation or the DOM (apart from `<audio>` elements for voice clips).
- `synth.js` — the instruments, as plain functions `(ctx, out, t, …)` that schedule their nodes at absolute context time: `tine` (kalimba/marimba), `bell` (FM), `pad`, `bass`, `noise` (filtered bursts), `kick`, `metal` (inharmonic FM clank), `blip`, `sweep`, `chirp` (birds), `cricket`; plus `noiseBuffer` and `impulseResponse` (a synthetic reverb room). They work on an `OfflineAudioContext` too.
- `music.js` — the procedural score. `SCORE` has one mood per phases-completed (0–4) plus the aftermath (5); all share D as tonal centre while the **mode darkens one note per milestone** (Ionian → Mixolydian → Dorian → Aeolian → Phrygian → Locrian) and the arrangement changes (kalimba tune + bells → shaker/woodblock → first metal tick → forge hammer + drone → heartbeat + b2 ostinato + distant industry → broken music box). `createMusic(ctx, { dry, wet, seed })` → `{ start, setMood(m, { instant, restSec }), silence, resume, scheduleUntil(t) }`: a lookahead scheduler on an eighth-note grid; melodies are composed per 8-bar phrase (`composePhrase`, seeded `rng`: motif, answer, motif over the third chord, cadence on the tonic; every fourth phrase rests). A mood change fades the current "section" gain (so notes already scheduled go silent), leaves room for the stinger, and starts the new mood on the next bar. `degreeFreq(mood, degree, octave)` gives a note in a mood's scale (used by musical cues).
- `sfx.js` — `CUES`: every effect as a recipe `(kit, t, opts)` with `kit = { ctx, out, wet, mood }`; `CUE_META` sets each cue's rate limit (`gap` ms) and level (balanced from offline loudness measurements). Musical cues (deliver with a climbing `combo`, upgrade, order done, phase stinger) play in the current mood's scale. Specials: `quindarIn`/`quindarOut` (NASA Quindar tones around a CAPCOM transmission), `reveal` (a cheerful jingle that tape-stops into a Phrygian hit), `ending` (timed to the ending's CSS animation: charge, beam 2.6 s, boom 3.2 s, debris, Moon+ ad jingle 6 s, final open fifth 18 s; with `variant: 'hq'` a shell whistles over to the impact and it closes on `endingFree`, a warm major chord, instead of the jingle and the open fifth; `afterEnding(free)` resumes the aftermath mood, or the bright mood 1 with birds after the HQ ending).
- `ambience.js` — `createAmbience(ctx, { out, wet })`: per-mood birds (gone by dusk), crickets at dusk, wind rising each phase, rumble and distant clangs at night, and the **factory hum**, whose level follows the number of working machines and whose pitch sags with `power.throttle` (brownouts are audible).
- Breaker sounds (`sfx.js`): `overload` (a two-tone alarm each beat of the countdown), `trip` (a clunk, sparks, the grid winding down), `reset` (relay click, spin-up); `recipe` is the selector click when a machine changes recipe. `audio.update` gets `overload` and `tripped` in its snapshot.
- `audio.js` — `createAudio()` → the engine: `unlock()` (creates/resumes the `AudioContext` on the first click or key press), the mixer (music and ambience each through a pause lowpass and a duck gain, effects, voice → master → compressor → makeup gain; one shared convolver reverb), `cue(name, opts)`, `update(dt, world)` (per-frame snapshot from `main.js`: mood, paused, throttle, working machines, order status/start, tech count; it detects transitions and cues phase stingers, the reveal, orders, research and brownouts, and muffles music while paused), `onEvents(events)` (deliveries chime), comms hooks for `ui.js` (`lineStart(line, { fresh })` → voice clip length in ms or null, `lineStop`, `commsIdle`), `ending`/`endingSkip`/`afterEnding`, and settings (`settings`, `setSettings`, `toggleMute`; volumes master/music/effects/voice + mute, saved in localStorage `selene.audio.v1`). The tab going hidden suspends the context.
- **Voice:** `voiceLines.js` enumerates every line DELTA (and NILE) can say exactly as `director.js` builds them, and `voiceKey(line)` hashes speaker + mood + text into the clip key (editing a line makes it a new key). `scripts/voice.mjs` records missing lines with ElevenLabs into `public/assets/voice/<key>.mp3` + `manifest.json` (`{ lines: { key: { file, ms, … } } }`), and Nolan's lines with `NIHIL_BOSS_VOICE_ID` (skipped without it), optionally several takes per line into `voice-takes/` (a stopped run resumes without re-recording finished takes) with a `review.html` where you choose a take per line and copy one `pick key n key n …` command; `pick-all [n]` takes take n for every line still without a clip. `try <delta|nile|boss> "<text>"` records any text in a voice into `voice-takes/try/` without touching the game. `listen` writes `voice-takes/listen.html`: every game clip with its text in play order, the newest batch on top (open it via the dev server, `http://localhost:5173/voice-takes/listen.html`). At runtime `audio.js` loads the manifest; a line with a clip plays through a light EQ (NILE: a PA-system band; Nolan: a warm low end and a little boardroom reverb), ducks music and ambience, and the comms text types along with it and holds until it ends. Lines without a clip stay text-only.
- `soundboard.js` — dev only: open the game with `?sounds` for buttons that play every cue, every music mood and the voice lines.

- Owns **order policy**: `issueOrder()` picks a product from `ORDER_POOL` for the current phase and random `target`/`ticks`/`reward` from the `ORDER_*` ranges (fewer of a dear product, more of a cheap one); a per-frame `tickOrders()` watcher issues the first order once phase 1 is done and auto-cycles a new one `ORDER_GRACE_TICKS` after the previous resolves.
- Owns **persistence** (localStorage key `lifeline.save.v2`, the pre-rename key kept so existing saves still load): `saveGame()` JSON-stringifies `{ ...serialize(), story: director.save(), visual: renderer.saveVisual() }` (autosave every 60 s, on each phase change and on `beforeunload`; never before a campaign starts); `loadGame()` parses, calls `loadState()`, then `renderer.reset()` + `renderer.loadVisual(data.visual)` + `renderer.applyEvents(events, 0)` to rebuild sprites and paving, clears transient drag/hover and restores the director. ## Conventions

- Coordinates are always `(x, y)` with `x` as the column. Keep the boundaries clean: simulation logic, recipes, and economy in `grid.js`/`config.js` (returning events), 3D drawing in `renderer.js` (+ `assets.js`, `environment.js`, `camera.js`), loop timing in `gameLoop.js`, DOM HUD in `ui.js`, input/wiring in `main.js`, campaign data in `campaign.js`, every player-facing string in `story.js`, story timing in `director.js`.
- **Sprite/event invariant:** an item has a sprite only between its `spawn` and `consume` events. Anything that destroys an in-transit item (e.g. `removeMachine`) must emit a `consume` so the sprite is cleaned up; items absorbed into a machine buffer are `consume`d on entry. On load this means **only `cell.item` is re-spawned** — never buffer contents or `pendingOutput`.
- **Economy invariant:** `STARTING_MONEY` must cover bootstrapping one full ore→product chain, and `PRODUCT_REWARD` must make a running chain net-positive, or the game stalls.
- To add a **machine type**: add it to `MACHINE_COST` (+ `PROCESS_TICKS` and `POWER_DRAW` if it processes), give it a `RECIPES` entry (processors) or handle it in `cellAccepts` + the relevant `updateFactoryLogic` phase, give it ports in `portsFor` (processor → `PROCESSORS`/`UPGRADABLE`; pure router → the movers phase), give it a case in `buildView` (renderer; add any new models to `MANIFEST` in `assets.js`), add a key to `BUILD_DEFS` (+ an `ICON` path) in `ui.js` a hotkey in `main.js` (+ `buildableTools`), and add it to the renderer's `PORT_TOOLS` and the `renderIcons` list. Machines serialize automatically as long as they stay plain data.
- To add an **item type / recipe**: add a mesh case to `createItemMesh` (assets), `ITEM_NAMES` (story) and a `RECIPES` entry (grid); give it a `SINK_VALUE` if the pad should buy it.
- To add a **story beat**: append to `BEATS` in `story.js` (list order = play order). Guard tutorial beats with conditions that turn false once the player is past that step, so they're skipped instead of arriving late.
- Machine types also need an entry in `BUILDING_NAMES`/`BUILDING_DESC` (story) and, if gated, a phase's `unlocks` (campaign).
- **Save format:** machines are stored as-is, so keep them plain JSON-able; `loadState` overlays saved fields onto `makeMachine` defaults, so adding a new machine field is backward-compatible. Bump `SAVE_VERSION` only for breaking changes.

## Verifying changes

There are no automated tests. Playwright (a devDependency) is available to drive the game in a real browser — `verify-flow.mjs` is a working example (`node verify-flow.mjs` with the dev server on :5173). Launch Chromium with `--use-angle=swiftshader --enable-unsafe-swiftshader --ignore-gpu-blocklist`, or headless WebGL renders blank. A script must clear `localStorage`, wait for **Begin Onboarding** (it appears once the models have loaded) and click it, then get cell positions from `window.__renderer.projectCell(x, y)` (the HUD panels sit on top of the canvas, so pick cells that aren't under the console, keys or comms) (page coordinates of a cell centre; move the camera with `window.__renderer.rig`). In dev builds `window.__sim` (the live `grid.js` module), `window.__campaign` and `window.__renderer` expose the real instances — e.g. `window.__sim.project.phase = 1` skips the first gate (a phase jump plays the completion juice: camera shake + zoom punch, so wait for the view to be still before clicking cells, as `verify-flow.mjs` does). Don't `import('/src/grid.js')` from the page: Vite's HMR timestamps can hand you a second, empty module instance (stateless modules like `synth.js`/`music.js`/`sfx.js` are fine to import, e.g. to render sounds on an `OfflineAudioContext` and measure peak/RMS). `window.__audio` is the live sound engine: `log` lists the cues played, `context`, `mood`, `speaking`, `musicDuck`. Avoid clicking cell `(0,0)` just to focus the page — that places a belt.
